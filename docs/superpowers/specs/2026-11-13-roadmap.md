# Roadmap after 0.2.0

Date: 2026-11-13. Each phase has its own design. The implementation plan
for a phase is written just before it's built, because later phases change
code that earlier phases touch.

| Phase | Design | What it adds | Plan | Status |
|---|---|---|---|---|
| 1. Hardening | `2026-11-13-phase1-hardening-design.md` | known-hash updates, pull main after merge, network retries, `/factory-uninstall`, CHANGELOG and `scripts/release` | `plans/2026-11-13-phase1-hardening.md` | done: built by the factory, PR #2 (2 rounds, $7.69) |
| 2. Prove it | `2026-11-13-phase2-prove-it-design.md` | `scripts/e2e` real-run scenarios and `scripts/eval` prompt evals, both capped and manual | `plans/2026-11-13-phase2-prove-it.md` | planned: issue #5, queued |
| 3. Visibility | `2026-11-13-phase3-visibility-design.md` | `job report`, daily digest issue comment, live dashboard strip | `plans/2026-11-13-phase3-visibility.md` | planned: filed, queue after phase 2 merges |
| 4. Safety after merge | `2026-11-13-phase4-post-merge-safety-design.md` | pause/resume, base-branch CI watch with revert PR, risky-change merge stop, secret scan before push | `plans/2026-11-13-phase4-post-merge-safety.md` | planned: filed, queue after phase 3 merges |
| 5. Scale | `2026-11-13-phase5-scale-design.md` | multi-part plans, Linux systemd runner, GitHub Actions runner with persisted state | `plans/2026-11-13-phase5a-multi-part-plans.md`, `…phase5b-linux-runner.md`, `…phase5c-actions-runner.md` | planned: three issues, queued one at a time after phase 4 |

Order matters in two places: phase 2's scenarios get extended for phases
3–5 as those land, and phase 4's pause is used by phase 5's runners. Phases
3 and 4 are otherwise independent.

Phases build one at a time: each later issue is filed with `factory:planned`
but without `factory`, and gets `factory` once the previous phase has merged
(2 → 3 → 4 → 5a → 5b → 5c), because they edit the same vendored files.
Cut a release (`scripts/release`) after each phase merges.
